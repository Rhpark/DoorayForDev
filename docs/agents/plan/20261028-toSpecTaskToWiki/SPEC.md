# Dooray 업무를 위키 문서로 정리 (dooray-task-to-wiki) — SPEC

## PRD

### Problem Statement

개발자는 Dooray 업무(이력)에서 개선 요청, 협의 결과, 바뀐 사용 방법 같은 지식을 얻는다. 그런데 이 지식은 업무 본문과 댓글 속에 흩어져 있다. 그래서 나중에 다른 개발자나 엔지니어가 "이 기능을 어떻게 설정하고 쓰는지" 찾으려면 관련 업무를 하나씩 뒤져야 한다.

위키에 정리하려면 업무를 읽고, 목적에 맞게 다시 쓰고, 화면 캡처 같은 이미지를 다시 올려 글 사이에 배치하고, 적당한 위치에 페이지를 만들어야 한다. 손이 많이 가서 잘 하지 않게 된다.

이미 있는 `dooray-report`는 "이 저장소 코드에 어떻게 적용할지"를 다루는 업무 한정 보고서이고, `wiki-write`는 받은 문구를 그대로 올리기만 한다. 업무를 위키 독자에 맞게 가공해 주는 도구는 없다.

### Solution

`/dooray-task-to-wiki <업무번호> [목적]`을 호출하면 에이전트가 다음 순서로 진행한다.

1. 업무 본문, 히스토리, 읽을 수 있는 첨부를 읽는다.
2. 요청한 목적(예: "A기능 사용방법 정의")에 맞게, 목적이 없으면 "이력 → 협의 결과"로, 개발자·엔지니어가 읽을 위키 문서 초안을 로컬에 쓴다.
3. 사용자는 대화로 초안을 고친다.
4. 검토가 끝나면 에이전트가 기존 위키 트리를 보고 위치를 제안하고, 사용자가 확인하거나 번호 목록에서 다른 위치를 고른다.
5. 업로드한다. 이때 초안에 넣어 둔 업무 이미지와 자료가 실제 형식으로 함께 올라간다. 이미지는 글 사이에 보이고 나머지는 첨부와 링크가 된다. 업무 링크도 함께 남는다.
6. 업로드한 초안은 그 위키 페이지 폴더로 옮겨 기록으로 남는다.

### User Stories

1. As a 개발자, I want `/dooray-task-to-wiki 242`처럼 업무번호만으로 위키 정리를 시작하고 싶다, so that 업무를 다시 읽고 옮겨 적는 수고를 덜 수 있다
2. As a 개발자, I want 업무번호 뒤에 "A기능 사용방법 정의"처럼 목적을 적고 싶다, so that 같은 업무라도 내가 남기려는 관점으로 문서가 만들어진다
3. As a 개발자, I want 목적 없이 호출하면 이력에서 협의 결과까지 정리되기를 원한다, so that 빠르게 업무 요약 문서를 남길 수 있다
4. As a 개발자, I want 에이전트가 업무 본문뿐 아니라 히스토리(댓글)까지 읽기를 원한다, so that 댓글에서 바뀐 결정 사항이 문서에 반영된다
5. As a 개발자, I want 에이전트가 읽을 수 있는 첨부(텍스트, 이미지, PDF 등)도 확인하기를 원한다, so that 첨부에만 있는 요구사항이나 화면이 빠지지 않는다

## SPEC

### Implementation Decisions

**구성**
- 새 에이전트형 Skill `dooray-task-to-wiki`를 Claude Code와 Codex 양쪽에 둔다. Codex에는 openai 메타를 포함하고 암묵 호출을 끈다.
  - Claude 쪽: opus/high, `disable-model-invocation: true`.
  - 대응하는 단일 CLI 명령은 없다(`dooray-report`와 같은 위치).
- 기존 CLI는 `wiki-write`만 확장한다. 내용 속 로컬 파일 업로드와 참조 변환, 초안을 페이지 폴더로 옮기는 옵션을 추가한다. 새 저수준 HTTP 함수로 파일 업로드를 추가한다.
- 표준 라이브러리만 쓴다(multipart 본문은 직접 만들고, 형식 추정은 `mimetypes`).

**업로드 API 계약** (서드파티 소스 + 2026-10-28 실측)
- 요청: `POST /wiki/v1/wikis/{위키ID}/pages/{페이지ID}/files`, `multipart/form-data`. 첫 필드 `type`(`inline_image` 또는 `general`), 다음 필드 `file`(파일 이름, `Content-Type`은 실제 형식).
- 서버가 307(또는 308)로 `Location`을 주면, 호스트가 `.dooray.com`으로 끝날 때만 같은 본문을 인증 헤더와 함께 그 주소로 다시 보낸다(실측: `file-api.dooray.com`). 다른 호스트면 보내지 않고 종료한다. 파이썬 `urllib`는 POST의 307을 따라가지 않으므로 직접 처리한다.
- 응답 201: `result{id, pageFileId, attachFileId, name, mimeType, type, size, createdAt, extension}`.
- 파일 형식을 `application/octet-stream`으로 보내면 저장 형식도 그렇게 되어, 클릭 시 확대 보기 대신 숫자 이름으로 다운로드된다(실측). 그래서 형식은 확장자로 추정하고, 모를 때만 `application/octet-stream`을 쓴다.

**본문 참조 형식** (실측: 프로젝트 ID·위키 ID 경로 모두 표시, Dooray 편집기는 프로젝트 ID 사용)
- 이미지: `![대체텍스트](/wikis/{프로젝트ID}/files/{attachFileId})`
- 그 밖의 파일: `[링크텍스트](/wikis/{프로젝트ID}/files/{attachFileId})`

**`wiki-write`의 로컬 파일 처리**
- 대상: 내용 속 마크다운 이미지 `![…](대상)`과 링크 `[…](대상)`.
  - 대상이 URL(스킴 있음), `/`로 시작하는 절대 경로(Dooray 참조 등), `#` 앵커이면 건드리지 않는다.
  - 공백이 있는 경로는 `(<경로>)` 형식으로 쓴다. 이 형식과 공백 없는 일반 형식을 모두 인식한다.
- 상대 경로의 기준은 `--file`을 쓰면 그 파일의 폴더, 직접 입력한 내용이면 현재 폴더(저장소 루트)다.
- 이미지 문법(`![…]`)은 `inline_image`, 링크 문법은 `general`로 올린다. 같은 파일을 여러 번 참조해도 한 번만 올리고 모든 참조를 같은 주소로 바꾼다.
- 위키에 무엇이든 쓰기 전에 참조한 로컬 파일이 모두 있는지 확인한다. 하나라도 없으면 그 목록과 함께 종료한다. `--dry-run`도 같은 검사를 하고, 기존 `생성 예정`/`이어쓰기 예정` 줄 아래에 `업로드 예정: <파일 이름> (이미지|첨부)` 목록을 보여준다.
- 순서
  - 이어쓰기: 대상 페이지에 파일 업로드 → 참조를 바꾼 내용으로 기존 규칙대로 날짜 헤더를 붙여 본문 수정.
  - 생성: 업로드할 파일이 없으면 지금처럼 한 번에 생성한다. 있으면 "페이지 생성(원문) → 새 페이지에 업로드 → 참조를 바꾼 본문으로 수정" 순서다. 업로드는 페이지가 있어야 할 수 있기 때문이다.
  - 중간에 실패하면 이미 만든 페이지 주소와 실패한 파일을 알리고 종료한다. 성공으로 보이지 않게 한다.
- 멘션 치환(`apply_mentions`)은 지금처럼 동작한다. 생성 문서에 `@이름`을 쓰지 않는 것은 Skill 규칙으로 지킨다.

**초안 옮기기 옵션**
- `wiki-write … --file <초안> --move-draft`: 쓰기가 모두 성공한 뒤에만 초안 파일을 대상 페이지 폴더(`위키 폴더/<위키이름>/<실제 제목>/…/`, 제목 금지 문자는 `_`)로 옮긴다. `download/`가 아니라 페이지 폴더 자체에 둔다.
- 같은 이름이 있으면 확장자 앞에 `_2`, `_3`…을 붙인다. 옮긴 위치를 출력한다.
- `--file` 없이 쓰거나 `--dry-run`과 함께 쓰면 옮기지 않는다.

**Skill 흐름 (`dooray-task-to-wiki`)**
1. 인자에서 업무번호와 목적(나머지 문구)을 나눈다. 업무번호가 없으면 묻는다.
2. `dooray full <번호>`(댓글 개수 제한 없음)로 본문·히스토리·파일 목록을 읽는다. 판단에 필요한 첨부를 `dooray download`로 받아 읽는다(`dooray-report` 공통 절차 1절과 같은 원칙: 읽은 것만 근거로 쓰고, 못 읽은 형식은 쓰지 않음). 업무 주소는 `dooray link`로 얻는다. 같은 업무의 `REPORT.md`가 있으면 참고만 한다.
3. 초안 `Dooray/wiki/<업무번호>_<목적>.md`(목적이 없으면 `<업무번호>_정리.md`, 금지 문자 `_`)를 쓴다. 같은 파일이 있으면 덮어쓰기 전에 알리고 확인을 받는다.
   - 독자는 개발자·엔지니어이고, 앱 공통 관점으로 쓴다. 목적이 있으면 그 목적에, 없으면 "이력 → 협의 결과"에 맞춘다.
   - 이해에 도움이 되는 업무 이미지는 글 흐름의 해당 위치에, 그 밖의 자료는 링크로 넣는다. 둘 다 초안 기준 상대 경로이고, 공백이 있으면 `(<경로>)` 형식이다.
   - 업무 출처(업무번호, 제목, 업무 주소)를 넣고, `@이름`은 쓰지 않는다.
4. 초안 전문을 보여주고 대화로 고친다.
5. 검토가 끝나면 `dooray wiki-list`로 트리를 보고 위치(새 페이지 경로 또는 기존 페이지)를 제안한다. 사용자가 확인하거나 `wiki-read` 번호 목록 탐색으로 고른다. 경로는 ` > `로 정리하고 따옴표로 감싼다. 대상이 이미 있으면 `dooray wiki-read`로 기존 내용을 읽고, 중복이면 초안을 조정할지 묻는다.
6. `dooray wiki-write "<경로>" --file <초안> --dry-run` 결과(생성/이어쓰기, 업로드 예정 파일)를 보여주고 명시적 확인을 받는다.
7. 확인되면 `--move-draft`를 붙여 실행하고, 위키 주소와 옮긴 초안 위치를 전달한다. 거절하면 쓰지 않는다.

**문서 갱신**
- `DOORAY.md`: Skill 표, `wiki-write` 설명(로컬 파일 업로드, `--move-draft`), 쓰기 규칙.
- README: Skill 표("에이전트가 필요한 것"), CLI 명령 설명.
- CLI 도움말.

### Testing Decisions

- **좋은 테스트의 기준:** 외부 동작만 검증한다. 입력은 CLI 인자와 초안 파일, 출력은 stdout과 종료 메시지, fake가 기록한 업로드(대상 페이지, 파일 이름, `type`, 형식, 바이트)와 쓰기 요청(본문), 옮겨진 초안 파일이다. 내부 함수의 호출 순서 자체가 아니라, 기록된 요청의 순서와 내용으로 판단한다.
- **seam:** 기존 위키 테스트와 같다. CLI main을 실행하고 `_api`(JSON), `_raw`(다운로드), 새 업로드 함수만 fake로 바꾼다. 위키 폴더 기준 경로는 임시 폴더로 바꾼다. fake 위키에 업로드 기록과 `attachFileId` 발급을 더한다.
- **사례**
  - 이어쓰기 + 로컬 이미지·xlsx: 업로드 2건(`inline_image`/`image/png`, `general`/xlsx 형식), 본문 참조가 `/wikis/<프로젝트ID>/files/<attachFileId>`로 바뀌고 날짜 헤더가 붙는다.
  - 생성 + 로컬 이미지: 기록 순서가 생성 → 새 페이지 ID로 업로드 → 바뀐 참조로 본문 수정이다.
  - 업로드할 파일이 없는 생성은 기존처럼 생성 1건으로 끝난다(기존 테스트 유지).
  - `(<공백 있는 경로>)` 참조, 같은 파일 두 번 참조(업로드 1건), URL·`/wikis/…`·`#` 링크는 그대로 둔다.
  - 로컬 파일이 없으면 업로드 0건, 쓰기 0건으로 오류가 나고 없는 파일 목록이 나온다(`--dry-run`에서도 같음).
  - `--dry-run`은 `업로드 예정` 목록을 출력하고 업로드·쓰기 0건이다.
  - `--move-draft`: 성공하면 초안이 `<위키 폴더>/Snoopy/<제목…>/`로 옮겨지고, 같은 이름이 있으면 `_2`가 붙는다. 실패하거나 `--dry-run`이면 옮기지 않는다.
- **리다이렉트 호스트 검사:** 보안 경계이므로 순수 함수로 분리해 단위 테스트한다(`file-api.dooray.com` 허용, 다른 호스트 거부).
- **기존 사례:** `tests/test_wiki.py`의 fake 위키와 `run()` 헬퍼, 임시 폴더로 바꾸는 방식(위키 다운로드 테스트)을 따른다. unittest(표준 라이브러리).
- **수동·실측:** multipart 본문과 307 재전송은 실제 Dooray 테스트 페이지에서 확인하고, 사용자가 웹에서 표시·클릭 동작을 확인한다. Skill 대화 흐름(초안 작성, 대화 수정, 위치 제안, 확인, 초안 이동)은 Claude Code와 Codex에서 직접 실행해 확인한다.

## Further Notes

- **근거의 한계:** 업로드 계약은 공식 문서가 아니라 서드파티 소스(`jon890/dooray-cli`)와 2026-10-28 실측에 근거한다. 공식 문서를 확보하면 교차 확인한다.
- **생성 중 실패:** 새 페이지를 만든 뒤 업로드가 실패하면 로컬 경로가 남은 본문으로 페이지가 남는다. 다시 실행하면 그 페이지에 이어쓰기가 되어 내용이 중복된다. 실패 메시지에 페이지 주소를 알려 사용자가 웹에서 정리하게 한다. 자동 정리(삭제)는 범위 밖이다.
- **옮긴 초안의 상대 경로:** 초안을 더 깊은 페이지 폴더로 옮기면, 초안 안의 업무 `download/` 상대 경로가 맞지 않게 된다. 옮긴 초안은 "무엇을 올렸는지"의 기록으로 보고 경로는 고치지 않는다.
- **"제목" 해석:** 사용자가 마지막에 말한 "업무번호_제목.md"를 목적 문구로 이해했다(`GRILL_ME.md` 참고). 업무 제목을 뜻한 것이라면 초안 이름 규칙만 바꾸면 된다.
- **선행 작업:** `docs/agents/plan/20261027-toSpecWiki/`의 위키 기능 위에서 동작한다.

## 2026-10-28 갱신 — 초안 형식 조정 (첫 실사용 후)

`/dooray-task-to-wiki 131`로 실제 문서(`Snoopy > Visualizer > 혼잡상태 지도 표시 정리 건`)를 올려 본 뒤 사용자가 결정했다. 위 Skill 흐름 3번의 초안 규칙을 이렇게 바꾼다.

- 본문 첫 줄에 제목(`# …`)을 쓰지 않는다. 위키 페이지 제목이 따로 표시되어 중복된다.
- 업무 상태 안내 문구(`> 상태: 아이디어…`)를 넣지 않는다. 확정 여부는 "제안된 …"/"아직 정해지지 않은 것" 같은 소제목으로 드러나고, 상태는 나중에 바뀌므로 출처 링크로 확인하게 한다.
- 출처는 맨 끝 한 줄로 둔다: `출처: 이력 #<업무번호> <업무 제목> — <업무 주소>`. 이 도구에서는 업무를 "이력"이라 부른다.
- 이미 올린 #131 페이지는 CLI에 본문 교체 기능이 없어(의도적 범위 밖) 사용자가 웹에서 고친다.

## 2026-10-28 갱신 — 옮긴 초안의 상대 경로를 새 위치 기준으로 고침

위 Further Notes의 "옮긴 초안의 상대 경로: … 경로는 고치지 않는다"는 이 시점부터 바뀐다(사용자 결정).

- `--move-draft`로 초안을 페이지 폴더로 옮길 때, 초안 속 로컬 이미지·파일 참조(`![…](경로)`, `[…](경로)`)를 새 위치 기준 상대 경로로 다시 계산해 바꾼다. 공백·괄호가 있으면 `(<경로>)`, 드라이브가 달라 상대 경로를 못 만들면 절대 경로로 둔다. URL·`/wikis/…`·`#` 링크와 링크 제목은 그대로다. 줄바꿈 형식은 유지한다.
- 이유: 옮긴 기록을 로컬에서 열면 이미지가 보이지 않고, 같은 파일을 다시 올리면 "로컬 파일이 없습니다"로 멈췄다.
- 테스트: 옮긴 뒤 경로가 `../../../../files/…`로 바뀌고, 그 경로로 같은 파일이 찾아지는지 검증한다.
- 이미 옮겨진 #131 기록(`Dooray/wiki/Snoopy/Visualizer/혼잡상태 지도 표시 정리 건/131_정리.md`)도 같은 규칙으로 경로를 고쳤다(새 위치에서 이미지 파일 존재 확인).
