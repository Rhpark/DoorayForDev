# Dooray 업무를 위키 문서로 정리 (dooray-task-to-wiki)

## 근거 자료

- 선행 작업 `docs/agents/plan/20261027-toSpecWiki/` — `wiki-list`·`wiki-read`·`wiki-write`·`wiki-download` 구현 완료. 경로는 `>`로 잇고 제목 우선으로 매칭한다. 쓰기는 "있으면 `## YY-MM-DD, HH:mm` 헤더로 이어쓰기, 없으면 부모 아래 생성"이고 `--dry-run` 확인을 거친다. 위키 주소는 `https://{TENANT}.dooray.com/wiki/{위키ID}/{페이지ID}`이다. 그 SPEC의 Further Notes에 `/dooray-task-to-wiki`를 후속으로 적었다.
- 저장 폴더 구조(2026-10-27 결정) — 업무는 `Dooray/task/report/<업무번호>/`(REPORT.md, `download/`), 위키는 `Dooray/wiki/<위키이름>/<제목>/.../download/`(실제 제목, 금지 문자 `_`). git은 `download/`만 제외하고 직접 작성한 문서는 추적한다.
- 기존 기능 — `dooray full <번호>`(본문·태그·댓글·파일 목록), `dooray download <번호> [파일명|번호|all]`, `dooray link <번호>`, `dooray-report` 공통 절차 1절(자료 확인), `Dooray.apply_mentions`(`@한글이름` → 실제 멘션).
- 실측: 위키 본문·댓글의 이미지 참조(읽기 전용, 2026-10-28)
  - `<img src="/wikis/4200118908792221669/files/<attachFileId>" alt="…" width="…">`(HD Map > SUMO Network 본문)
  - `![이름](/wikis/4200118908792221669/files/<attachFileId>)`(주간 미팅 노트 댓글)
  - 가운데 숫자는 위키 ID가 아니라 프로젝트 ID다. 끝 숫자는 다운로드용 `id`가 아니라 `attachFileId`다.
- 서드파티 근거: `jon890/dooray-cli` 소스(`src/api/client.ts`의 `uploadWikiPageFile`, `src/utils/wiki-snippet.ts`)
  - 업로드: `POST /wiki/v1/wikis/{위키ID}/pages/{페이지ID}/files` multipart. `type`(`general`|`inline_image`)을 `file`보다 먼저 보낸다. 307이면 `location`으로 인증 헤더를 실어 다시 보낸다(호스트 확인).
  - 본문 삽입: `![name](/wikis/{wikiId}/files/{attachFileId})`(위키 ID 사용).
  - 페이지 생성 응답에 `id`가 있다.
  - `jhl8041/dooray-mcp`는 생성 시 `attachFileIds`만 지원하고 업로드 함수는 없다.
- 공식 문서: `🔌 Dooray! API > 서비스 API`와 `파일 업/다운로드 관련 API 가이드`가 있으나 JS 렌더링이라 읽지 못했다. Chrome 확장은 사용자가 설치하지 않기로 했다.
- 실측: 업로드·삽입 시험(사용자 승인, 테스트 페이지 `Snoopy > Visualizer > CLI 쓰기 테스트` — 이전 테스트 페이지는 사용자가 지워서 다시 생성)
  - 1차: `Content-Type: application/octet-stream`으로 png·txt 업로드. 두 번 모두 307 → `file-api.dooray.com` 재전송 → 201. 응답에 `id, pageFileId, attachFileId, name, mimeType, type, size, createdAt, extension`. 참조 A(프로젝트 ID 이미지)·B(위키 ID 이미지)·C·D(파일 링크) 모두 표시됐다. 다만 클릭하면 확대 보기 대신 숫자 이름으로 다운로드됐다(사용자 확인).
  - 원인 확인: 기존 파일은 `Content-Type: image/png`·xlsx 형식으로 내려오는데 업로드한 것은 `application/octet-stream`이었다.
  - 2차: `image/png`·`text/plain`으로 다시 업로드하니 서버 `mimeType`도 그대로 저장됐다. E(마크다운 이미지)·F(`<img>` 태그) 표시 정상, G(파일 링크) 다운로드 정상(사용자 확인).
  - 새 페이지 생성 후 `위키 주소` 출력도 정상(생성 응답 `id` 확인).
- 해석·가정
  - 사용자가 마지막에 말한 "업무번호_제목.md"의 "제목"은 호출 때 적는 목적 문구로 이해했다(직전 제안이 `<업무번호>_<목적>.md`였음).
  - 2차 시험 결과의 "잘 보인다/잘 다운받아진다"를 클릭 시 확대 보기와 정상 파일 이름까지 해결된 것으로 받아들였다.

## 결정사항

- 호출은 `/dooray-task-to-wiki <업무번호> [목적]`이다(예: `242 A기능 사용방법 정의`). 경로는 인자로 받지 않는다.
- 자료는 업무 본문, 히스토리(댓글), 읽을 수 있는 첨부다. `REPORT.md`가 있으면 참고만 하고 그대로 쓰지 않는다 — 위키 독자는 개발자·엔지니어이고 앱 공통 문서(실행 시 설정 방법, 변경 방법 등)가 될 수 있기 때문이다.
- 목적이 있으면 그 목적으로 위키에 맞게 정리한다. 목적이 없으면 "이력 → 협의 결과"로 단순 정리한다.
- 고정 템플릿은 보류한다 — 써 본 경험에서 정한다.
- 초안을 로컬에 먼저 저장하고 대화로 고친다. 파일 이름은 `Dooray/wiki/<업무번호>_<목적>.md`, 목적이 없으면 `<업무번호>_정리.md`이다(업무 간 이름 충돌 방지·출처 추적). 파일 이름에 못 쓰는 문자는 `_`로 바꾼다. 같은 이름이 있으면 덮어쓰기 전에 알린다.
- 쓸 위치는 초안 검토가 끝나고 업로드할 때 정한다. 기존 트리를 보고 제안하며, 번호 목록 탐색으로 바꿀 수 있다. 대상 페이지가 이미 있으면 기존 내용을 먼저 읽는다.
- 업로드할 때 초안을 그 페이지 폴더로 옮긴다. 같은 이름이 있으면 `_2`처럼 번호를 붙인다.
- 업무 이미지와 자료가 이해에 도움이 되면 위키에 올린다. 이미지는 글 흐름에 맞는 위치에 보이게 하고, 업무 링크를 함께 둔다.
- 초안에는 업무에서 받은 파일을 로컬 경로로 넣는다. 업로드할 때 `wiki-write`가 실제 형식으로 올리고 Dooray 참조로 바꾼다(이미지 `inline_image`, 그 밖은 `general` + 링크).
- 업로드할 때 파일 형식(`Content-Type`)을 실제 형식으로 보낸다 — `octet-stream`이면 클릭 시 숫자 이름으로 다운로드된다(실측).
- 본문 참조는 Dooray 편집기와 같은 프로젝트 ID 경로를 쓴다(프로젝트 ID·위키 ID 모두 표시됨을 실측).
- 멘션은 쓰지 않는다.
- 쓰기 전 `--dry-run` 확인은 기존 `wiki-write` 규칙을 그대로 따른다.
- 테스트 seam: CLI main 실행 + `_api`·`_raw`·새 업로드 함수만 fake로 바꾼다. Skill 대화 부분은 수동 확인.
- 작업 폴더 slug는 `toSpecTaskToWiki`(Dooray 업무번호 없음).

## Q&A

- **Q:** (사용자) 이제 `dooray-task-to-wiki`를 기획하자.
  **A:** 이미 정해진 것(형식, `wiki-write` 재사용, opus 에이전트형)과 흐름 초안을 제시했다. 흐름은 `full`·`download`로 자료 확인 → 대상 페이지가 있으면 읽기 → 로컬 초안 → 초안·`--dry-run` 확인 → `wiki-write --file` 업로드 → 경로 없으면 번호 목록 탐색이다. 정할 것 다섯 가지를 권장안과 함께 물었다. 자료 범위(`REPORT.md` 참고), 고정 뼈대, 초안 위치(`task/report/<번호>/WIKI.md`), 첨부는 올리지 않음, 멘션 쓰지 않음.

- **Q:** (사용자) 호출은 `/dooray-task-to-wiki 번호`. `REPORT.md`는 참고만 하고 그대로 쓰지 않는다 — 위키는 개발자·엔지니어 대상이고 앱 공통이 될 수 있다(예: 실행 시 설정 방법, 변경 방법). 2·3·4·5·6번 흐름은 맞다. 답: 1) 본문·히스토리·첨부를 파악해 사용자가 요구하는 목적으로 정리한다(예: `/dooray-task-to-wiki 242 A기능 사용방법 정의`). 2) 템플릿은 경험에서 나와야 하니 보류. 3) 실제 작성은 위키이니 로컬도 `Dooray/wiki/<위키>/.../`여야 하지만 위치가 아직 없으니 `Dooray/wiki/`에 요구사항.md를 임시로 만들자. 4) 이해에 도움이 되면 업무 이미지·자료를 올리고 업무 링크도 둔다. 5) 멘션은 뺀다. 질문이 있나?
  **A:** 네 가지를 물었다. 1) 경로가 없으니 위치를 어떻게 정할지(초안 후 제안 권장), 2) 목적이 없을 때(묻기 권장), 3) 초안 파일 이름과 업로드 후 처리(업무번호로 나누기, 페이지 폴더로 옮기기, 시각 붙인 이름 권장), 4) 이미지 업로드 API와 본문 삽입 문법을 아직 모른다(실제 GNSS 페이지는 이미지 3개인데 본문 참조 없음).

- **Q:** (사용자) 1) 초안 검토가 끝나 업로드할 때 어디로 올릴지 물으니, 그때 옮기자. 2) 목적이 없으면 이력 → 협의 결과로 단순 정리. 3) `[목적].md`, 목적이 비면 `정리.md`. 4) 찾아볼까?
  **A:** 읽기 전용으로 조사했다. 실제 위키 본문·댓글에서 `<img src="/wikis/<프로젝트ID>/files/<attachFileId>">`와 `![…](/wikis/…/files/…)` 참조를 찾았다. 커뮤니티 MCP에는 업로드 함수가 없었고, `dooray-cli` 소스에서 업로드 계약(multipart, `type` 먼저, 307 재전송, 응답 `attachFileId`)과 삽입 문법(위키 ID 경로)을 확인했다. 페이지가 먼저 있어야 업로드할 수 있다. 초안에 로컬 경로를 넣고 업로드 때 CLI가 올려 바꾸는 방식을 제안하고, 테스트 페이지 시험 승인을 요청했다.

- **Q:** (사용자) 기본적으로 Dooray API를 보고 되는지 파악해야 하지 않나? 그리고 다른 파일과 달리 이미지는 글과 함께 보일 수 있잖아?
  **A:** 둘 다 맞다. 공식 문서 두 페이지(서비스 API, 파일 업/다운로드 가이드)는 JS 렌더링이라 (a) Chrome 확장으로 열거나 (b) 붙여넣기가 필요하다. 이미지는 `inline_image`로 본문에 보이고, 그 밖의 파일은 `general` 첨부와 링크가 된다.

- **Q:** (사용자) 어떤 방법이 더 좋은 정보를 얻을 수 있나?
  **A:** (a)가 낫다. 전체 내용, 표·코드 예시, 관련 페이지를 따라갈 수 있기 때문이다. (b)라면 `Ctrl+A` 전체 복사가 좋다.

- **Q:** (사용자) a로 진행하자.
  **A:** Chrome 확장을 불러왔으나 사용자가 설치하지 않기로 했다. (b) 붙여넣기 방법(파일 가이드 전체, 서비스 API의 위키 절)을 안내했다.

- **Q:** (사용자) 그냥 확인은 내가 해볼게, 너가 테스트해봐. 내가 웹에서 제대로 올라갔는지 확인할게.
  **A:** 테스트 페이지가 삭제되어 있어 같은 이름으로 다시 만들었다. 1차로 png(`inline_image`)·txt(`general`)를 `octet-stream`으로 업로드했다(307 → `file-api.dooray.com` → 201). 본문에 A(프로젝트 ID 이미지)·B(위키 ID 이미지)·C·D(파일 링크)를 이어썼다.

- **Q:** (사용자) A·B·C·D 다 보인다. 첨부 목록도 잘 받아진다. 그런데 A·B 이미지를 클릭하면 확대 대신 바로 다운로드되고 파일 이름이 숫자다. C·D도 숫자 이름으로 받아진다.
  **A:** API로 비교해 보니 기존 파일은 실제 형식, 업로드한 파일은 `application/octet-stream`이었다. 2차로 `image/png`·`text/plain`으로 다시 올리고 E(마크다운 이미지)·F(`<img>` 태그)·G(파일 링크)를 이어썼다.

- **Q:** (사용자) E·F 잘 보인다. G도 잘 다운받아진다.
  **A:** 확정 사항을 정리했다(업로드 계약, 실제 형식 필수, 참조 형식, 생성 → 업로드 → 수정 순서, 생성 후 주소). 남은 두 가지를 물었다. 1) 초안 이름 충돌 시 번호 붙이기, 2) 초안에 로컬 경로를 넣고 업로드 때 변환.

- **Q:** (사용자) 1) `정리.md`는 중복될 수 있으니 `이력번호_정리.md`로 하자. 2) 그래. 1번에 대한 내 의견은 어떤가?
  **A:** 좋다. 목적이 있는 초안에도 같은 접두어를 붙여 `<업무번호>_<목적>.md`로 통일하자고 했다. 같은 업무·목적 재실행(업로드 전)은 알림 후 덮어쓰기, 페이지 폴더로 옮길 때 같은 이름이면 `_2`, 금지 문자는 `_`로 바꾼다.

- **Q:** (사용자) 그래 너의 말처럼 업무번호_제목.md로 하자.
  **A:** "제목"을 목적 문구로 이해했다고 밝히고 확정 기획을 정리했다.

- **Q:** (에이전트, /to-spec) 테스트 seam을 CLI main + `_api`·`_raw`·새 업로드 함수 fake로 잡고, Skill 대화 부분은 수동 확인하려 한다. 맞나? 작업 폴더 이름은?
  **A:** (사용자) 이대로. 폴더 이름은 `toSpecTaskToWiki`.

## 미해결 질문

- 공식 API 문서 본문은 읽지 못했다. 업로드 계약은 서드파티 소스와 실측에 근거한다.
- 새 페이지를 만든 뒤 업로드가 중간에 실패하면, 로컬 경로가 남은 본문으로 페이지가 남는다. 재실행하면 이어쓰기가 되어 중복될 수 있다. 처리 방식은 구현하면서 정하고 사용자에게 알린다.
- 초안을 페이지 폴더로 옮기면, 초안 안의 상대 경로(업무 `download/`를 가리킴)가 깨진다. 옮긴 초안은 기록 용도로 보고 그대로 둘지 확인이 필요하다.
- 테스트 페이지 `Snoopy > Visualizer > CLI 쓰기 테스트`는 사용자가 확인 후 웹에서 지운다.
