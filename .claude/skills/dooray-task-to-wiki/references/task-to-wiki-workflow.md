# Dooray 업무 → 위키 공통 절차

업무 하나의 본문·히스토리·확인한 첨부를, 그 업무를 모르는 개발자·엔지니어가 읽을 앱 공통 위키 문서로 정리한다. Claude와 Codex는 이 절차를 함께 사용하고 파일 작성·자료 판독 도구는 각 `SKILL.md`의 지침을 따른다.

모든 CLI 명령은 저장소 루트에서 실행한다. 위키 경로는 `>` 앞뒤를 공백 한 칸으로 맞춰 따옴표로 감싸고, `DOORAY.md`의 공통 실행·쓰기 규칙을 따른다. 조회 결과는 초안의 근거로 사용하고 사용자에게는 검토할 초안 전문을 전달한다.

Windows PowerShell에서 Python 보조 검사를 실행할 때는 경로·본문의 한글이 전달 중 손상되지 않도록 다음을 지킨다.

- 한글 경로·본문을 삽입한 Python 코드를 here-string 등의 파이프로 `python -`에 전달하지 않는다. Windows PowerShell 5.1의 `$OutputEncoding`이 ASCII이면 Python에 도착하기 전에 `?`로 치환되며, `-X utf8`만 추가해도 복구되지 않는다.
- 짧은 검사 코드는 ASCII로 작성하고 경로는 따옴표로 감싼 별도 명령행 인자로 전달한다. Python에서는 `sys.argv`로 받는다. 예: `python -X utf8 -c "from pathlib import Path; import sys; print(Path(sys.argv[1]).is_file())" "초안경로"`.
- 긴 검사 코드나 한글을 포함한 코드는 각 환경의 파일 편집 도구로 UTF-8 `.py` 파일에 저장한 뒤 `python -X utf8 "검사파일.py" "초안경로"`로 실행한다. 초안의 본문은 Python 코드에 삽입하지 않고 파일에서 읽는다.
- 검사 파일에서 문서를 읽고 쓸 때는 `encoding="utf-8"`을 명시한다. 검사 대상 초안과 이미지·첨부의 원본 경로가 정상적으로 열리는지 확인한다.

1. 인자를 업무번호와 목적(나머지 문구)으로 나눈다. 업무번호가 없으면 묻는다. 목적이 없으면 "이력 → 협의 결과" 정리로 한다.
2. 초안을 쓰기 전에 자료를 읽는다.
   - `dooray full 업무번호`를 댓글 개수 제한 없이 실행해 본문·히스토리·파일 목록을 읽는다.
   - 판단이나 문서에 필요한 첨부·이미지는 `dooray download 업무번호 파일명-또는-번호`로 받아 직접 확인한다. 읽지 못한 형식이나 범위의 내용은 추측하지 않는다.
   - 업무 주소는 `dooray link 업무번호`로 얻는다.
   - `Dooray/task/report/<업무번호>/REPORT.md`가 있으면 참고만 하고 그대로 옮기지 않는다.
3. 초안을 `Dooray/wiki/<업무번호>_<목적>.md`에 쓴다. 목적이 없으면 `<업무번호>_정리.md`로 하고, 파일 이름에 못 쓰는 `<>:"/\|?*`는 `_`로 바꾼다. 기존 초안을 새로 덮어써야 하면 먼저 알리고 확인을 받는다.
   - 독자는 이 업무를 모르는 개발자·엔지니어다. 앱을 쓰는 관점(설정 방법, 변경 방법, 동작 방식 등)으로 쓰고, 지정한 목적에 맞게 구성한다.
   - 업무 본문·히스토리·직접 확인한 첨부에서 확인한 사실만 쓴다. 업무 안에서 정해지지 않은 것은 정해진 것처럼 쓰지 않는다.
   - 이해에 도움이 되는 이미지는 설명하는 위치에 `![설명](경로)`로, 그 밖의 자료는 `[설명](경로)`로 넣는다. 경로는 초안 기준 상대 경로(`../task/report/<업무번호>/download/<파일>`)이고 공백이나 괄호가 있으면 `(<경로>)`로 감싼다. 업로드와 Dooray 참조 변환은 CLI가 처리한다.
   - 본문 첫 줄에 제목(`# …`)을 쓰지 않는다. 위키 페이지 제목이 따로 표시된다. 업무 상태 안내 문구(예: `> 상태: 아이디어…`)도 넣지 않는다. 상태는 나중에 바뀌고 출처 링크로 확인할 수 있다.
   - 맨 끝에 출처를 한 줄로 둔다: `출처: 이력 #<업무번호> <업무 제목> — <업무 주소>`
   - 생성 문서에 `@이름`을 쓰지 않는다. 업로드할 때 실제 멘션으로 바뀌어 알림이 간다.
4. 저장한 초안을 다시 읽고 경로와 전문을 보여준다. 사용자의 요청대로 수정하고 검토 완료를 밝힐 때까지 반복한다.
5. 올릴 위치를 정한다. `dooray wiki-list`로 트리를 보고 새 페이지 경로나 기존 페이지를 제안한다. 사용자가 다른 곳을 원하면 `dooray wiki-read "경로 >"`의 전체 번호 목록을 답변에 보여주고 한 단계씩 고르게 한다. 목록을 일부 선택지로 줄이지 않고 사용자의 답을 기다린다. 대상 페이지가 이미 있으면 `dooray wiki-read "경로"`로 기존 내용을 읽고, 겹치는 내용이 있으면 초안을 조정할지 묻는다. 초안을 조정하면 바뀐 내용을 다시 검토받는다.
6. 게시할 내용과 첨부를 확정한 뒤 판단만 실행한다.

```text
dooray wiki-write "경로" --file "초안경로" --dry-run
```

   `생성 예정`/`이어쓰기 예정`, 대상 경로, 검토한 본문, `업로드 예정` 파일 목록을 보여주고 명시적 게시 확인을 받는다. 이어쓰기면 `## YY-MM-DD, HH:mm` 헤더가 붙는다고 알린다. 오류(없는 로컬 파일, 없는 경로 등)면 그대로 알리고 멈춘다. 대상·내용·첨부가 달라지면 판단과 게시 확인을 다시 진행한다.
7. 확인되면 실행한다.

```text
dooray wiki-write "경로" --file "초안경로" --move-draft
```

   성공하면 위키 주소와 옮긴 초안 위치를 전달한다. CLI가 초안을 위키 트리 모양의 폴더로 옮기고 로컬 링크를 새 위치 기준으로 조정한다. 같은 파일명이 있으면 `_2` 등의 이름으로 보존한다. 게시를 거절하면 업로드하지 않고 검토한 로컬 초안을 남긴다.

실패하면 출력 전체를 그대로 알리고 자동으로 재시도하지 않는다. 이미 만들어진 페이지 주소나 업로드된 파일 안내도 함께 전달한다. 본문 변경으로 이어쓰기가 중단되면 최신 내용을 읽고 확인한 뒤 다시 진행한다. CLI가 쓰기 완료를 확인하기 전에는 초안을 옮기지 않는다.

업무 댓글·상태와 저장소 코드는 변경하지 않는다. 글은 API 토큰 소유자 명의로 작성된다. 본문의 게시 확인과 도구 실행 권한은 별개이며, 실행 권한은 각 환경의 정책을 따른다.
