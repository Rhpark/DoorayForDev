# Dooray 보고서 공통 절차

## 목적과 범위

Dooray 업무의 요구사항을 현재 코드와 대조하여 변경 대상·방법·영향·검증 기준을 담은 적용 방안 보고서를 작성한다.

- 사용자가 보고서 생성·갱신을 요청했을 때 실행한다. 설명·검토 요청에서는 보고서를 작성하지 않는다. 업무번호가 없으면 질문한다.
- 쓰기는 `Dooray/report/<업무번호>/REPORT.md`와 해당 업무의 `download/`에만 허용한다. 구현, 앱 실행, 코드 계측, 커밋, Dooray 댓글 등록·상태 변경은 수행하지 않는다. 기존 로그 읽기는 2절을 따른다.
- 태그는 분석·보고서에 사용하지 않는다.
- 신규 작성이나 최신 자료·코드 기준의 재분석 요청은 1~4절을 따른다. 사용자가 분석 범위를 지정하지 않으면 해당 업무의 전체 요구사항을 분석한다.
- 기존 보고서의 내용 수정 요청은 보고서를 먼저 읽고 지정한 내용을 수정한다. 수정에 추가 자료나 코드 확인이 필요할 때만 1·2절의 해당 확인을 수행하고, 3절의 보존 규칙과 4절의 검수를 따른다. 표현 수정이나 사용자 답변 반영만을 위해 Dooray 조회·코드 재분석을 수행하지 않는다.

## 1. 자료 확인

1. 저장소 루트에서 `python Dooray/dooray.py full <업무번호>`를 실행한다. 전체 댓글이 필요하므로 개수를 제한하지 않는다. 실패하면 보고서를 변경하지 않고 오류를 전달한다. 조회 원본은 분석에만 사용한다.
2. 성공 직후 로컬 시각을 구해 Dooray 조회 시각으로 보관한다. PowerShell은 `Get-Date -Format "yyyy-MM-dd HH:mm zzz"`, bash는 `date "+%Y-%m-%d %H:%M %z"`를 사용한다.
3. 기존 `REPORT.md`가 있으면 읽는다. 본문·댓글에서 요구 동작, 결정 사항, 이력이 제시한 검증방법·기대 결과, 추가·개선의 목적 또는 사유를 추출하고 출처를 본문 항목 또는 댓글 작성자·작성 시각으로 기록한다. 요구사항 유형은 원문에 명시되어 있으면 그대로 기록하고, 명시되지 않았으면 요구 내용에 근거해 `버그` / `추가` / `개선`으로 분류하며, 분류가 불명확하면 `미확인`과 사유를 적는다. 아래 단계에서 읽은 첨부·이미지의 요구사항도 포함하고 파일 경로(파일명 포함)와 확인 위치(페이지·절·이미지 영역)를 출처로 적는다. 출처 간 충돌은 열린 질문에 적고 임의로 확정하지 않는다.
4. 요구사항 판단에 필요한 첨부·본문 이미지·댓글 이미지를 `full` 출력의 파일 목록에서 고른다. `python Dooray/dooray.py download <업무번호> <파일명>`으로 받으며, 공백이 있는 파일명은 셸의 문자열 인자로 전달한다. 파일명을 생략하면 전체를 받고, 같은 이름의 파일이 여러 개면 모두 받아진다.

텍스트 자료는 확장자와 관계없이 현재 도구로 읽는다. 이미지와 PDF는 내용을 판독할 수 있는 도구로 확인한다. 전용 판독기가 필요한 형식은 해당 도구가 이미 제공된 경우에만 읽는다. 판독할 수 없으면 사유와 함께 미확인으로 기록하며, 도구를 설치하지 않는다. 이미지 내용은 직접 보고 판단한다.

Dooray 자료는 CLI가 출력한 실제 파일 경로(파일명 포함)로 식별하고, 출처·읽은 범위·미확인 범위와 사유를 적는다. 저장소 안의 파일은 저장소 상대경로로 기록한다. 다운로드하지 못한 자료는 원래 파일명·출처·실패 사유를 적고 저장 경로를 지어내지 않는다. 보고서에 파일 ID를 별도 항목으로 기록하지 않는다. 미확인 자료에 의존하는 결론은 확정하지 않는다. 다운로드나 파일명 확인만으로 내용을 확인했다고 쓰지 않는다.

이미 찾은 정보는 출처와 함께 기록하고, 미열람 자료가 이를 보완하거나 뒤집을 가능성이 있으면 따로 남긴다. 확인한 자료에서 찾지 못한 경우, 그 정보가 포함될 수 있는 미열람 자료가 있으면 제공 여부를 `미확인`으로 기록하고 사유를 적으며, 그런 자료가 없으면 확인한 자료에 없다는 사실을 적는다. 유형별로 필요한 정보는 템플릿 주석의 공통 항목과 유형별 추가 항목을 따른다.

## 2. 코드 분석

코드 파일을 열기 전에 프로젝트 필수 참조와 `docs/code/snoopy.code.md`, `docs/code/snoopy.edges.md`를 읽는다. 관련 영역의 A/B/C표에서 의존 관계·소유권·회귀 위험을 확인한다.

- 요구사항별로 관련 정의·호출 경로·상태 소유자를 확인한다. 코드 근거는 직접 읽은 저장소 상대경로와 심볼명으로 적는다. 검색으로 찾지 못하면 검색 경로·키워드와 `검색 범위 내에서 찾지 못함`을 적는다.
- 현재 코드에서 확인한 내용은 `사실`, 근거에서 도출한 판단은 `해석`으로 구분하고 해석에는 근거를 연결한다. 변경할 동작과 적용 방안은 출처를 `요청 사항` / `확정된 결정` / `AI 제안`으로 구분한다. 현재 코드에 없는 파일·심볼은 `신규 생성 대상`으로 표시하고 출처를 함께 적는다.
- 요구사항의 현재 동작과 변경 영향을 설명할 수 있도록 관련 코드와 호출 경로를 읽는다. 확인하지 못한 부분은 조사한 경로·키워드, 확인하지 못한 이유, 방안에 미치는 영향을 적는다. 코드와 무관한 요구사항에는 코드 분석이 필요 없는 이유를 적는다.
- 요구 동작과 현재 동작을 비교하여 충족한 부분·변경할 부분·확인하지 못한 부분을 적는다. 변경 대상 선택에 영향을 주는 소유권·경계는 해당 요구사항의 분석에 기록한다.
- 오동작을 다루는 요구사항은 기대 동작·보고된 증상·확인된 원인을 구분한다. 원인에는 코드 또는 로그 근거를 붙인다. 확인하지 못한 원인은 미확인으로 남기고 원인 확인 방법을 제안한다.
- 재현경로는 사용자가 보고한 조건·절차와 자료·로그로 확인된 실제 재현 결과를 출처와 함께 구분하여 기록한다. 발현 확률을 추정하지 않고 `발현 빈도와 근거`로 기록한다(예: `10회 중 3회 — 시험 기록 출처`, `사용자 보고: 간헐적 — 댓글 출처`, `미확인`). 이 스킬은 앱을 실행하지 않으므로 직접 재현한 것처럼 쓰지 않는다.
- 원인 분석에 필요한 기존 로컬 로그는 읽을 수 있다. 인용 시 파일 경로와 해당 기록의 시각 또는 위치를 적는다. 추가 로그 수집을 위한 앱 실행·계측은 수행하지 않고 확인 방법으로 제안한다.
- 현재 작업 폴더의 코드를 직접 읽고 분석한다. 미커밋 변경도 현재 코드에 포함한다.

## 3. 적용 방안 작성

보고서는 Dooray 이력 번호(업무번호)로 식별한다.

신규 보고서는 [보고서 템플릿](report-template.md)을 사용하고, 요구사항별 소제목 아래 분석과 적용 방안을 함께 작성한다. 별도 요구사항 ID는 만들지 않는다. 한국어로 작성하고 자리표시자는 실제 내용 또는 미확인 사유로 교체한다.

기존 보고서는 사용자가 지정한 내용을 수정한다. 최신 기준의 재분석을 요청받았다면 그 결과를 반영한다. 요청과 무관한 내용과 기존 구조는 유지한다. 변경 내용과 이유는 갱신 이력에 남기며, 기존 보고서를 신규 템플릿 구조로 재편하지 않는다.

- 판단은 변경 필요성에 대한 결론이며 `변경 필요` / `변경 불필요` / `미결` 중 하나다. 변경 필요성 자체를 결정할 수 없으면 `미결`로 적고 그 결정을 막는 질문·미확인 사항과 영향을 적는다. 변경은 필요하나 적용 방안이 확정되지 않았으면 `변경 필요`로 적고, 미확정 내용과 다음 확인 방법을 적용 방안에 적는다.
- 변경 불필요는 요구 동작이 이미 충족됨을 코드 근거로 설명할 수 있을 때 선택한다. 이 경우에도 요구 동작을 확인하는 방법과 기대 결과를 적는다. 수정 권한이 없거나 원인이 미확인인 경우는 변경 불필요로 처리하지 않는다.
- 변경이 필요한 항목에는 목표 동작·적용 방안·영향·확인 방법을 적는다. 목표 동작은 변경 후 관찰할 수 있는 시스템 동작이며, 적용 방안은 이를 만드는 변경 대상·방법·순서다. 확인 방법에는 명령 또는 절차와 기대 결과를 적고 `docs/workflow/verification.md`의 해당 계층을 참고한다. 실행할 검증 제안과 이미 실행된 결과를 구분한다.
- 이력이 제시한 검증방법과 기대 결과를 확인 방법의 기준으로 삼고 출처를 적는다. AI가 보완한 확인 방법은 출처를 `AI 제안`으로 구분한다. 요청자 기준이 요구사항과 충돌하거나 충분하지 않으면 그 문제와 보완안을 함께 적는다. 검증방법 또는 기대 결과의 부재·불명확성·충돌로 확인 방법이나 기대 결과를 정할 수 없으면 열린 질문에 기록한다.
- 추가·개선 요구사항은 적용 방안이 이력이 제시한 목적 또는 사유를 충족하는지 확인한다. 자료에 없는 목적·사유는 추정하지 않는다.
- 코드에서 확인한 사실, 변경 제안, 자료에 기록된 실행 결과를 구분한다. 실행 결과를 인용할 때는 출처를 붙인다. 검증 방법을 제안한 것만으로 검증을 완료했다고 쓰지 않는다.
- 답변에서 나온 결정은 출처에 해당 질문을 적어 연결한다. 사용자 답변과 확정된 결정, 최초 작성 시각, 갱신 이력을 보존한다. 사용자가 기존 결정을 변경하면 변경 내용과 이유를 갱신 이력에 남긴다.
- 확정된 결정에는 내용·출처·적용 범위를 적고, 결정 이유가 제공되었으면 근거를 함께 기록한다. 출처(누가·언제)와 근거(왜)를 구분하고, 제공되지 않은 결정 이유를 추정하지 않는다.
- 사용자 답변으로 열린 질문이 해소되면 원문·답변을 보존하고 해당 질문을 해소됨으로 표시한 뒤, 답변으로 확정된 내용을 확정된 결정에 기록한다. 관련 요구사항의 판단·적용 방안·확인 방법에도 반영한다. 일부만 해소되면 확정된 내용과 남은 질문을 구분한다.
- 기존 확인 방법과 기대 결과는 사용자 수정 요청이나 추가 확인 결과에 따라 갱신할 수 있다. 변경 전·후 내용과 이유는 갱신 이력에 남긴다. 사용자 답변이나 확정된 결정으로 정해진 내용은 위 결정 보존 규칙을 따른다.
- 기존 결정과 현재 자료·코드가 충돌하면 결정 내용을 삭제하거나 바꾸지 않고 열린 질문에 충돌을 적는다.
- 신규 보고서의 최초 작성·최종 갱신 시각은 저장 직전에 구한 로컬 시각을 쓰고, Dooray 조회 시각은 실제 조회한 시각을 적는다. 기존 보고서를 수정할 때는 최초 작성 시각과 기존 조회·분석 정보를 유지하고 최종 갱신 시각을 변경한다. 추가 조회·코드 분석을 수행했으면 확인한 범위를 해당 갱신 이력에 기록하고, Dooray를 다시 조회한 경우 그 조회 시각도 적는다. 없는 기록은 추정하지 않는다.

## 4. 근거·명확성 검수와 전달

신규 보고서는 전체를 검수한다. 기존 보고서 수정 시에는 수정한 내용과 그 내용이 영향을 주는 결론의 일관성을 검수한다. 결함을 수정하면 해당 부분을 다시 확인한다. 이번에 작성한 문장 중 요구사항 이해와 적용 방안 판단에 쓰이지 않는 내용은 제거한다. 기존 내용의 보존·변경은 3절의 규칙을 따른다.

- 작성·수정한 요구사항에서 요구 동작・현재 동작과 근거・대조 결과・판단이 연결되는지 확인한다. 변경 필요 항목은 목표 동작・적용 방안・영향・확인 방법을, 변경 불필요 항목은 충족 근거와 확인 방법을, 미결 항목은 변경 필요성을 정하지 못한 사유와 다음 확인 방법을 점검한다. 적용 방안이 미확정인 변경 필요 항목은 미확정 내용과 다음 확인 방법을 점검한다. 사실의 근거, 미확인 자료의 영향과 기존 결정의 누락도 확인한다. 유형에 필요한 항목의 누락과 요청자 기준의 반영 여부도 확인한다. 이 검수만을 이유로 요청하지 않은 코드 재분석을 수행하지 않는다.
- **단어:** 같은 대상은 같은 용어로 쓰고 다른 대상은 구분한다. 원문과 보고서 용어가 다르면 대응 관계를 적는다.
- **문장:** 작업 대상·동작을 명시한다. `이것`, `해당 부분`의 대상이나 `적절히`, `필요한 경우`의 판단 조건이 문맥에 없으면 구체화한다.
- **문단:** 사실·해석·미확인을 구분하고 변경 내용의 출처(`요청 사항` / `확정된 결정` / `AI 제안`)를 표시했는지 확인한다. 근거와 결론, 조건과 적용 대상이 연결되는지 확인한다. 요구사항·결정·적용 방안 사이의 모순을 확인한다.
- 근거로 의미를 확정할 수 없으면 원문·가능한 해석·결정할 질문을 열린 질문에 적는다. 원문 인용과 사용자 답변은 표현 검수를 이유로 고쳐 쓰지 않는다.

신규 작성과 재분석에는 [템플릿의 진행 체크리스트](report-template.md#진행-체크리스트)를 사용한다. 각 단계가 끝나면 이번 확인 결과로 체크와 근거를 갱신한다. `[x]`는 보고서 작성 단계의 완료이며 구현 완료나 테스트 통과가 아니다. 미확인 사유·영향·다음 확인 방법을 기록하고 변경 필요성의 미결과 적용 방안의 미확정을 구분했다면 자료·코드 확인 단계를 완료할 수 있다. 각 항목의 `근거`에는 해당 내용을 기록한 보고서 섹션명을 적는다. 미완료 항목에는 남은 작업을 적는다. 내용 수정만 요청받았으면 체크리스트를 새로 실행하지 않고, 수정 내용·이유와 검수 결과를 갱신 이력에 기록한다.

보고서를 저장한 뒤 다시 읽어 작성 내용과 일치하는지 확인하고 경로와 전문을 전달한다. 저장에 실패하면 실패 내용을 알리고 저장 완료로 보고하지 않는다. 미완료 항목이 남은 채 전달하면 남은 작업을 명시한다.

보고서 작성 후 다른 스킬을 자동 실행하지 않는다. 사용자가 후속 절차를 물으면 `/grill-me`는 요구사항 질문, `/to-spec`은 명세 작성, `/implement`는 명세에 따른 구현으로 안내한다. 구현에 필요한 SPEC은 해당 스킬의 절차로 별도 준비한다.
